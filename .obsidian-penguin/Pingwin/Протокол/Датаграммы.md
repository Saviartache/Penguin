# Датаграммы

Расширенный `CONNECT` (RFC 9220) на [[Опознание|опознанном]] соединении:

```
:method     CONNECT
:protocol   connect-udp
:scheme     https
:authority  <имя сервера>
:path       /.well-known/pingwin/udp
```

- Ответ `200` открывает канал; клиент ждёт его, прежде чем слать.
- Канал — одна UDP-сессия приложения с адресом на каждой посылке: отдельного
  запроса на собеседника нет.
- Закрытие — конец или сброс потока запроса.

## Формат

Датаграмма HTTP/3 (RFC 9297, §2.1):

```
+----------------------+------------+--------+----------+
| Quarter Stream ID (i)| Context ID | адрес  |  данные  |
+----------------------+------------+--------+----------+
|      varint          |  0x00 (i)  | SOCKS5 |   ..     |
+----------------------+------------+--------+----------+
```

| Поле | Значение |
|---|---|
| Context ID | всегда 0, как в RFC 9298; иное — отбрасывается |
| адрес | запись SOCKS5: тип (`0x01` IPv4, `0x03` имя, `0x04` IPv6), адрес, порт 2 байта |
| направление адреса | от клиента — куда, от сервера — откуда |

Не помещается в датаграмму QUIC — отправитель отбрасывает с ошибкой: границы
посылки — это и есть UDP.

## По HTTP/2

[[Перенос по TCP|По TCP]] датаграмм QUIC нет: тот же запрос (расширенный
`CONNECT`, RFC 8441, с `capsule-protocol: ?1`), а содержимое — от Context ID
до данных — едет капсулами `DATAGRAM` в теле потока (RFC 9297, §3.5):

```
+------------------+------------+-------------------------------+
| Capsule Type (i) | Length (i) | Context ID ‖ адрес ‖ данные    |
+------------------+------------+-------------------------------+
|      0x00        |   varint   |  как выше                     |
+------------------+------------+-------------------------------+
```

Капсулы чужих типов пропускаются. Длина больше датаграммы UDP с самым длинным
адресом — поток закрывается.

См. также [[Потоки]], [[Ошибки Pingwin]].
