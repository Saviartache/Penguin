# Pingwin

Формат провода. По этому документу можно написать вторую реализацию.

Эталон — этот каталог и `servers/pingwin`. Разошлось с текстом — верен код.

---

## 1. Что это

Прокси поверх HTTP/3 (RFC 9114). На проводе — обычное соединение QUIC с
сайтом: настоящий TLS 1.3, настоящий сертификат, ALPN `h3`. HTTP/1.1 и
HTTP/2 нет ни в какой роли.

| Свойство | Чем достигается |
|---|---|
| на проводе — обычный HTTP/3 | QUIC v1, TLS 1.3 с сертификатом на имя сервера |
| сервер не подменить | сертификат проверяется как обычно **и** сервер доказывает владение ключом X25519 |
| пароль не перебрать по перехвату | доказательство выведено из X25519 и экспорта TLS |
| повтор опознания бесполезен | экспорт TLS свой у каждого соединения |
| активная проверка бесполезна | не узнав клиента, сервер отвечает как статический сайт |
| одно соединение на всё | потоки — запросы `CONNECT`, датаграммы — датаграммы HTTP/3 |

Нет: HTTP/1.1, HTTP/2, смены порта, 0-RTT, своего шифрования поверх QUIC.

---

## 2. Обозначения

- `X25519(a, B)` — RFC 7748, сырой результат.
- `Extract` / `Expand` — HKDF на SHA-256, RFC 5869.
- `Exporter(метка, контекст, длина)` — экспорт ключей TLS 1.3, RFC 8446, §7.5.
- `b64` — base64 алфавитом для URL без дополнения (RFC 4648, §5).
- `‖` — склейка.

| Величина | Значение |
|---|---|
| метка выводов | `"pingwin"` |
| метка экспорта | `"EXPORTER-pingwin"`, контекст пустой, 32 байта |
| длина ключа | 32 байта |
| ALPN | `h3` |

---

## 3. Соединение

QUIC v1 (RFC 9000), TLS 1.3, ALPN `h3`. Имя в SNI — имя сервера, сертификат
выписан на него и проверяется клиентом обычным способом. Самоподписанный
сертификат не годится.

Сервер объявляет в `SETTINGS` `SETTINGS_ENABLE_CONNECT_PROTOCOL = 1`
(RFC 9220) и `SETTINGS_H3_DATAGRAM = 1` (RFC 9297), а в параметрах QUIC —
`max_datagram_frame_size` (RFC 9221).

---

## 4. Ключи

У сервера постоянная пара X25519: открытая половина в профиле клиента,
закрытая в настройках сервера. У каждого пользователя свой пароль.

```
exporter   = Exporter("EXPORTER-pingwin", "", 32)
ss         = X25519(эфемерный клиента, постоянный сервера)

user       = Expand(Extract(постоянный сервера, пароль), "pingwin user", 8)
prk        = Extract(exporter, ss ‖ пароль)
client     = Expand(prk, "pingwin client", 32)
server     = Expand(prk, "pingwin server", 32)
```

`ss` посчитает только владелец закрытого ключа сервера, `exporter` — только
стороны этого соединения TLS, пароль — только пользователь. Сертификат
доказывает имя, `server` — ключ: подмена требует обоих.

---

## 5. Опознание

Первый запрос соединения, до любого `CONNECT`:

```
:method        GET
:scheme        https
:authority     <имя сервера>
:path          /
authorization  Pingwin b64(эфемерный клиента ‖ user ‖ client)
```

Токен — 72 байта до кодирования: 32 + 8 + 32.

Сервер по порядку:

1. Схема `Pingwin`, токен разбирается, длина 72.
2. `user` есть в таблице.
3. `client` совпадает с посчитанным (сравнение за постоянное время).

Прошло — соединение опознано, ответ:

```
:status        204
pingwin-proof  b64(server)
```

Не прошло — ответ тот же, что на `GET /` без заголовка (§8). Клиент, не
получивший `204` с верным `pingwin-proof`, закрывает соединение: это отказ
опознания.

Опознаётся **соединение**, а не запрос: дальше запросы идут без токена.
Клиент шлёт их только после ответа `204`.

---

## 6. Потоки

Классический `CONNECT` (RFC 9114, §4.4) на опознанном соединении:

```
:method     CONNECT
:authority  <хост>:<порт>      IPv6 в квадратных скобках
```

Имя разрешает сервер. Тело запроса — байты к цели, тело ответа — от неё.
Конец тела — полузакрытие направления; сброс потока — обрыв.

- Соединился — `200`, затем тело.
- Не соединился — `502`, в теле причина (UTF-8, не длиннее 1024 байт).

**Ответа никто не ждёт.** Клиент отдаёт поток приложению сразу и пишет тело
следом: ожидание стоило бы оборота на каждом соединении. Ответ ждёт первое
чтение; не `2xx` становится его ошибкой с причиной из тела. Отсюда требование
к серверу: тело, пришедшее до соединения с целью, придерживается, а не
выбрасывается.

---

## 7. Датаграммы

Расширенный `CONNECT` (RFC 9220) на опознанном соединении:

```
:method     CONNECT
:protocol   connect-udp
:scheme     https
:authority  <имя сервера>
:path       /.well-known/pingwin/udp
```

Ответ `200` открывает канал; клиент ждёт его, прежде чем слать. Канал —
одна UDP-сессия приложения с адресом на каждой посылке: отдельного запроса на
собеседника нет.

Датаграмма HTTP/3 (RFC 9297, §2.1) этого запроса:

```
+----------------------+------------+--------+----------+
| Quarter Stream ID (i)| Context ID | адрес  |  данные  |
+----------------------+------------+--------+----------+
|      varint          |  0x00 (i)  | SOCKS5 |   ..     |
+----------------------+------------+--------+----------+
```

- **Context ID** — всегда 0, как в RFC 9298; другое значение отбрасывается;
- **адрес** — запись SOCKS5: тип (`0x01` IPv4, `0x03` имя, `0x04` IPv6),
  адрес, порт двумя байтами. От клиента — куда, от сервера — откуда.

Датаграмма, не помещающаяся в датаграмму QUIC, отбрасывается отправителем с
ошибкой: границы посылки — это и есть UDP. Канал закрывается концом или
сбросом потока запроса.

---

## 8. Что видит тот, кого не узнали

Статический сайт. На любой запрос неопознанного соединения сервер отвечает
так, как ответил бы обычный сервер статических файлов:

| Запрос | Ответ |
|---|---|
| `GET`, `HEAD` существующего файла | `200`, файл |
| `GET`, `HEAD` каталога | его `index.html` |
| `GET`, `HEAD` чего-то другого | `404` |
| любой другой метод, включая `CONNECT` | `405` |

Опознание, не прошедшее проверку, неотличимо от запроса без него.

---

## 9. Порядок ошибок

| Что случилось | Что делает сторона |
|---|---|
| сертификат не проверился | клиент: обрыв, ошибка настроек |
| ответ на опознание не `204` или `pingwin-proof` не тот | клиент: отказ опознания |
| `CONNECT` до опознания | сервер: §8 |
| цель недостижима | сервер: `502` с причиной |
| не `2xx` на `CONNECT` | клиент: ошибка первого чтения, с причиной |
| датаграмма с Context ID не 0 или без адреса | получатель: отбрасывает |

Отказ опознания означает не тот пароль или не тот ключ сервера; отличить одно
от другого нельзя и не нужно — лечатся одинаково. Обрыв связи посреди
рукопожатия отказом не считается: это повод повторить попытку.

---

## 10. Ссылка-приглашение

```text
pingwin://<пароль>@<хост>:<порт>?key=<ключ>&sni=<имя>#<профиль>
```

- **пароль** и **профиль** — процентное экранирование всего, что не буква,
  цифра и `-._~`;
- **хост** — IPv6 в квадратных скобках;
- **порт** — необязателен, по умолчанию 443;
- **`key`** — открытый ключ сервера, `b64`;
- **`sni`** — необязательно: имя в сертификате, если оно не совпадает с
  хостом.

Собирает ссылку сервер (`pingwin-server link`), разбирает клиент. Общего кода
у них нет (`AGENTS.md` §1), формат связан образцом — одна строка в тесте на
обеих сторонах.
