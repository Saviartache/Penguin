# Pingwin, версия 1

Формат провода. По этому документу можно написать вторую реализацию.

Эталон — этот каталог и `servers/pingwin`. Разошлось с текстом — верен код.

---

## 1. Что это

Прокси поверх TCP. На проводе выглядит соединением TLS 1.3. Внутри —
мультиплексор: сколько угодно потоков TCP и датаграммных каналов в одном
соединении.

| Свойство | Чем достигается |
|---|---|
| поток неотличим от TLS 1.3 | настоящий `ClientHello` браузера, дальше только записи данных |
| опознание не видно | AEAD в `SessionID`; ключ — из X25519 с постоянным ключом сервера |
| активная проверка бесполезна | не узнав клиента, сервер отдаёт соединение прикрытию |
| прямая секретность | второй X25519, эфемерный с обеих сторон |
| первый запрос без оборотов | 0-RTT: `OPEN` уезжает вместе с приветствием |
| повтор ранних данных невозможен | окно эфемерных ключей + отметка времени |
| длины записей ничего не выдают | расписание дополнения выведено из ключа |

Нет: смены порта, сжатия, согласования версий, возобновления сессии.

---

## 2. Обозначения

- `X25519(a, B)` — RFC 7748, сырой результат.
- `HKDF-Extract` / `HKDF-Expand` — RFC 5869 на SHA-256.
- `AEAD` — AES-256-GCM либо ChaCha20-Poly1305 (признак в §4.2). Метка 16
  байт, нонс 12.
- Числа старшим байтом вперёд. `‖` — склейка.

| Величина | Значение |
|---|---|
| метка версии | `"pingwin1"` |
| длина ключа | 32 байта |
| длина `SessionID` | 32 байта |
| окно времени | ±120 с |
| наибольшее тело записи | 16384 байта |

---

## 3. Ключи

У сервера постоянная пара X25519: открытая половина в профиле клиента,
закрытая в настройках сервера. У каждого пользователя свой пароль — он не
заменяет ключ.

```
ss_s = X25519(эфемерный клиента, постоянный сервера)
ss_e = X25519(эфемерный клиента, эфемерный сервера)

probe   = Expand(Extract("", ss_s), "pingwin1 probe", 32)
user    = Expand(Extract(постоянный сервера, пароль), "pingwin1 user", 8)

zero    = Expand(Extract(SHA-256(запись ClientHello), ss_s ‖ пароль),
                 "pingwin1 0rtt", 32)

prk     = Extract(SHA-256(запись ClientHello ‖ запись ServerHello),
                  ss_s ‖ ss_e ‖ пароль)
c2s     = Expand(prk, "pingwin1 c2s", 32)
s2c     = Expand(prk, "pingwin1 s2c", 32)
pad_c2s = Expand(prk, "pingwin1 pad c2s", 32)
pad_s2c = Expand(prk, "pingwin1 pad s2c", 32)
```

`ss_s` опознаёт обе стороны, `ss_e` даёт прямую секретность, пароль разделяет
пользователей одного сервера. Склейка приветствий однозначна: обе половины —
записи TLS с длиной в первых пяти байтах.

## 4. Рукопожатие

```
клиент                                          сервер
  │  [ложное приветствие]                        │   не часть протокола, §8
  │  16 03 01 …  ClientHello                     │
  │  14 03 03 00 01 01  ChangeCipherSpec         │
  │  17 03 03 …  одна запись ранних данных       │   если признак 0-RTT
  ├─────────────────────────────────────────────►│
  │◄─────────────────────────────────────────────┤
  │  16 03 03 …  ServerHello                     │
  │  14 03 03 00 01 01  ChangeCipherSpec         │
  │  17 03 03 …  записи данных                   │
```

### 4.1. `ClientHello`

Настоящее приветствие TLS с отпечатком браузера. Требований два:

1. В `key_share` есть доля X25519 (`0x001d`) длиной 32 байта — эфемерный ключ
   клиента. Доли других групп разрешены и пропускаются.
2. `SessionID` — ровно 32 байта с данными опознания (§4.2).

Имя в SNI — имя прикрытия; протокол его не использует.

### 4.2. Данные опознания

Открытый текст, 16 байт:

```
+--------+----------+-------------+--------------------+
| версия | признаки | время (6)   | метка пользователя |
|   1    |    1     |  секунды    |         8          |
+--------+----------+-------------+--------------------+
```

- **версия** — `1`; другое значение отвергается;
- **признаки** — бит 0: дальше одна запись ранних данных; бит 1: разговор
  идёт ChaCha20-Poly1305 (иначе AES-256-GCM); остальные нули;
- **время** — шесть младших байт секунд от начала эпохи;
- **метка** — `user` из §3.

Шифруется AES-256-GCM (независимо от бита 1 — выбор шифра здесь ещё не
известен) на ключе `probe`, нонс нулевой, дополнительные данные — **всё
сообщение `ClientHello` с обнулённым `SessionID`**. Результат, 32 байта, и
есть `SessionID`.

Нулевой нонс безопасен: `probe` выведен из эфемерного ключа клиента, то есть
свой на каждое соединение.

### 4.3. Что проверяет сервер

По порядку; отказ на любом шаге ведёт к §7.

1. Запись — рукопожатие, сообщение — `ClientHello`, есть доля X25519,
   `SessionID` длиной 32.
2. `SessionID` расшифровывается ключом `probe`.
3. Версия равна 1.
4. `|время клиента − время сервера| ≤ 120 с`.
5. Эфемерный ключ клиента не встречался за последние 120 с.
6. Метка пользователя есть в таблице.

Пункты 4 и 5 вместе закрывают повтор целиком.

### 4.4. Ранние данные

При поднятом бите 0 за `ChangeCipherSpec` идёт **ровно одна** запись,
зашифрованная ключом `zero`. Внутри — кадры (§6): обычно `OPEN` первого потока
и первые данные к нему.

Ровно одна, а не «сколько пришлёт»: иначе понадобилось бы сообщение о конце
ранних данных. Прямой секретности у ранних данных нет — `zero` выведен без
`ss_e`; это свойство любого 0-RTT.

### 4.5. `ServerHello`

Обычное сообщение TLS 1.3 в режиме совместимости:

- `legacy_version` = `0x0303`, `random` — 32 случайных байта;
- `session_id` — эхо клиентского, 32 байта;
- `cipher_suite` = `0x1301`, сжатие 0;
- расширения `supported_versions` (`0x002b` = `0x0304`) и `key_share`
  (`0x0033`) с эфемерным ключом сервера.

Дальше — `ChangeCipherSpec` и записи данных. Как и у настоящего TLS 1.3,
больше в открытом виде не показывается ничего.

## 5. Записи

```
+------+---------+--------+------------------------------+
| 0x17 | 0x0303  | длина  | AEAD(кадры) ‖ метка 16 байт  |
+------+---------+--------+------------------------------+
|  1   |    2    |   2    |            длина             |
+------+---------+--------+------------------------------+
```

Тело — не длиннее 16384 байт, открытого текста в записи не больше 16368.

Нонс не пишется: 12 байт, число от младшего байта к старшему, плюс единица
после каждой операции. Счётчики направлений независимы и начинаются с нуля;
у ключа ранних данных свой.

Записи `ChangeCipherSpec` (`0x14`) пропускаются при чтении в любом месте.
Другие типы после рукопожатия — ошибка.

Отсюда требование к реализации, которое дороже, чем кажется: **запись уходит
в сокет целиком или не уходит вовсе**. Половина записи на проводе означает,
что у собеседника не сойдётся метка следующей, — то есть одна брошенная
посреди отправки задача обрывает всю сессию, а не свой поток. Практический
вывод: писать должен тот, кого нельзя отменить.

### 5.1. Дополнение

Каждая сторона выводит расписание из своей затравки (`pad_c2s` у клиента,
`pad_s2c` у сервера):

```
цель(i) = 512 + (затравка[2i] ‖ затравка[2i+1]) mod 1024,   i < 6
цель(i) = 0,                                                i ≥ 6
```

Перед шифрованием i-й записи отправитель дописывает кадр `PAD` так, чтобы
открытый текст стал **не короче** цели. Осталось меньше семи байт — пустой
`PAD` всё равно добавляется: иначе по остатку восстанавливается исходный
размер. Получатель ничего не считает — `PAD` просто выбрасывается.

## 6. Кадры

Внутри одной записи — сколько угодно кадров подряд.

```
+---------+-----------+--------+----------+
| команда |   поток   | длина  |  данные  |
+---------+-----------+--------+----------+
|    1    |     4     |   2    |  длина   |
+---------+-----------+--------+----------+
```

| Код | Имя | Кто шлёт | Данные |
|---|---|---|---|
| `0x00` | `PAD` | оба | что угодно; выбрасывается |
| `0x01` | `OPEN` | клиент | адрес назначения (§6.1) |
| `0x02` | `OPEN_OK` | сервер | нет |
| `0x03` | `OPEN_ERR` | сервер | причина, UTF-8 |
| `0x04` | `DATA` | оба | байты потока |
| `0x05` | `FIN` | оба | нет |
| `0x06` | `RST` | оба | причина, UTF-8 |
| `0x07` | `UDP_BIND` | клиент | нет |
| `0x08` | `UDP` | оба | адрес ‖ датаграмма |
| `0x09` | `PING` | оба | нет |
| `0x0A` | `PONG` | оба | нет |

Номера потоков раздаёт **только клиент**, начиная с 1 и не переиспользуя. Ноль
— номер кадров вне потоков. Поток, открытый ранними данными, всегда первый.

`FIN` закрывает одно направление, `RST` обрывает поток целиком; кадры потока
после `RST` игнорируются.

**`OPEN_OK` никто не ждёт.** Клиент отдаёт поток приложению сразу за `OPEN` и
шлёт данные следом, не дожидаясь ответа: ожидание стоило бы оборота на каждом
соединении. `OPEN_OK` остаётся знаком, что цель ответила, а `OPEN_ERR`
приезжает туда же, куда приехали бы данные, и становится ошибкой первого
чтения. Отсюда требование к отправителю: `OPEN` и первые `DATA` должны уехать
в исходном порядке — сервер обязан придержать данные до того, как соединится с
целью, а не выбросить их.

**6.1. Адрес** — запись SOCKS5: тип (`0x01` IPv4, `0x03` имя, `0x04` IPv6),
адрес, порт двумя байтами. Имя разрешает сервер.

**6.2. Датаграммы** — `UDP_BIND` открывает канал, сервер отвечает `OPEN_OK` и
заводит сокет. Дальше кадры `UDP` в обе стороны. Датаграмма, не помещающаяся в
кадр, отбрасывается отправителем с ошибкой: границы посылки — это и есть UDP.

**6.3. Живость** — `PING` раз в 30 с, `PONG` в ответ. Молчание дольше 95 с —
соединение мёртвое. Ею же меряют задержку: открытие потока для этого не
годится, оно не ждёт ответа и покажет ноль.

---

## 7. Что делает сервер, не узнав клиента

Не отвечает отказом и не рвёт соединение, а открывает соединение к прикрытию
(настоящему сайту), отдаёт ему всё прочитанное и дальше переливает байты.
Прочитанное отдать обязательно: без начала запроса прикрытие ответит не тем,
чем ответило бы само по себе, — и эта разница выдаёт сервер.

| Что пришло | Когда сервер сдаётся |
|---|---|
| чужое приветствие | после двух подряд (столько нужно обходу DPI, §8); следующего ждёт не дольше секунды |
| заголовок не похож на TLS (`GET / HTTP/1.1`) | сразу: тип не из `20..24` либо старший байт версии не `0x03` |
| больше 64 КиБ до опознания | сразу |
| ничего нового до конца срока | сразу, если что-то уже прочитано |

Соединение, по которому не пришло ничего, закрывается без прикрытия — обычный
веб-сервер тоже не ждёт запроса вечно.

---

## 8. Обход DPI

Не часть протокола. Клиент вправе отдать первую посылку как угодно: разрезать,
переставить куски, послать перед ней ложную копию с малым TTL. Байты самой
посылки при этом не меняются.

Единственное требование к серверу — пропустить ложную посылку. Она устроена
как ещё одно приветствие, не проходящее опознание, и правило §7 закрывает этот
случай, не заводя метки, которую можно искать в трафике.

Приёмы и их границы — в документе `penguin_transport::desync`.

## 9. Порядок ошибок

| Что случилось | Что делает сторона |
|---|---|
| `SessionID` не расшифровался | сервер: §7 |
| версия, время, повтор, неизвестный пользователь | сервер: §7 |
| метка записи не сошлась | обрыв соединения |
| кадр объявил длину больше остатка записи | обрыв соединения |
| `OPEN` на клиенте, `OPEN_OK` без ожидающего | обрыв соединения |
| цель недостижима | сервер: `OPEN_ERR` с причиной |
| `OPEN_ERR` на живом потоке | клиент: ошибка первого чтения, с причиной от сервера |
| половина записи на проводе | обрыв соединения: следующая запись не расшифруется |

Отказ опознания клиент видит не отказом, а ответом прикрытия — обычно
`HTTP/1.1 400`. Называть это надо отказом опознания, а не «сервер ответил не
по протоколу»: искать надо в двух полях профиля, а не в сети. Отличить «не тот
пароль» от «не тот ключ» нельзя и не нужно — лечатся одинаково.

Обрыв связи посреди рукопожатия отказом не считается: это повод повторить
попытку.

## 10. Ссылка-приглашение

```text
pingwin://<пароль>@<хост>:<порт>?key=<ключ>&sni=<прикрытие>#<имя>
```

- **пароль** и **имя** — процентное экранирование всего, что не буква, цифра
  и `-._~`;
- **хост** — IPv6 в квадратных скобках;
- **порт** — необязателен, по умолчанию 443;
- **`key`** — открытый ключ сервера, base64 алфавитом для URL и без
  дополнения: `+` у половины клиентов означает пробел;
- **`sni`** — имя прикрытия.

Остального в ссылке нет: у отпечатка, шифра и 0-RTT рабочие умолчания, а обход
DPI подбирают под сеть клиента, а не под сервер.

Собирает ссылку сервер (`pingwin-server link`), разбирает клиент. Общего кода
у них нет (`AGENTS.md` §1), формат связан образцом — одна строка в тесте на
обеих сторонах.
